# 15. Git и автоматизация: рабочий минимум

Книга, по мотивам которой сделан курс, подробно разбирает Phing, ручные сборочные скрипты и виртуалки для окружения. Учить это сегодня не нужно: Phing 2 давно не развивается, Vagrant вытеснен контейнерами, а сборка PHP-проекта свелась к Composer. Идея осталась прежней и она важная: **всё, что вы делаете руками больше двух раз, должно запускаться одной командой**.

Код главы: `course/code/Ch15/`.

```bash
php course/code/Ch15/check.php
```

## Три инструмента, которые закрывают почти всё

**Composer** — зависимости и точки входа. Скрипты в `composer.json` играют роль, которую раньше выполняли make-файлы и Phing-таргеты:

```json
"scripts": {
    "test": "phpunit",
    "lint": "php Ch15/check.php"
}
```

Новый человек в проекте запускает `composer install`, `composer test`, `composer lint` — и ему не нужно знать, где лежат бинарники и какие у них флаги.

**PHPUnit** — автоматическая проверка поведения (глава 14).

**Git** — история и точки возврата. Остальное (статический анализ, форматирование, контейнеры) добавляется по мере необходимости, а не заранее.

## Своя проверка одной командой

`Ch15/check.php` обходит все файлы примеров, проверяет синтаксис через `php -l` и наличие `declare(strict_types=1)`:

```php
match (true) {
    $status !== 0 => $problems[] = "синтаксис: {$path}: " . implode(' ', $output),
    !str_contains((string) file_get_contents($path), 'declare(strict_types=1)') => $problems[] = "нет strict_types: {$path}",
    default => null,
};
```

Скрипт возвращает код выхода `1`, если нашёл проблемы, — это обязательное условие для любой автоматизации: и Git-хук, и CI смотрят именно на код выхода, а не на текст в консоли.

В реальном проекте вместо самописной проверки берут готовые: `phpstan`/`psalm` (статический анализ), `php-cs-fixer`/`phpcs` (стиль), `rector` (миграции). Ставятся они так же — в `require-dev` и в скрипт.

## Git: минимум, который экономит время

- **Маленькие коммиты с осмысленным сообщением.** Сообщение отвечает на вопрос «зачем», диф уже показывает «что». Коммит должен оставлять проект в рабочем состоянии.
- **Ветка на задачу.** `git switch -c feature/lazy-albums`, работа, пул-реквест, слияние. Долгоживущие ветки болезненно расходятся с основной.
- **`.gitignore` с первого дня.** В репозиторий не попадают `vendor/`, кеши, артефакты сборки и локальные настройки IDE. Для примеров курса это `course/code/.gitignore`.
- **`composer.lock` в репозитории** для приложений (глава 13) — чтобы у всех и на сервере ставились одинаковые версии.
- **`git bisect`**, когда «раньше работало»: несколько шагов двоичного поиска по истории находят коммит, который сломал поведение. Работает только при маленьких коммитах — вот и практическая причина их делать.

## Хук, который не даёт закоммитить сломанное

В репозитории лежит образец `course/code/Ch15/pre-commit.sample`:

```bash
php course/code/Ch15/check.php
composer -d course/code test
```

Установка:

```bash
cp course/code/Ch15/pre-commit.sample .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit
```

Хуки живут в `.git/hooks` и не версионируются, поэтому образец хранят в репозитории, а установку описывают в README (или автоматизируют скриптом `post-install-cmd` в Composer).

Правило одно: хук должен быть быстрым. Пара секунд — терпимо, минута — и его отключат через `--no-verify`.

## CI: то же самое, но у всех

Локальные проверки легко обойти, поэтому те же команды повторяют на сервере. Образец для GitHub Actions лежит в `course/code/Ch15/ci.yml.sample`; включается копированием в `.github/workflows/`. Содержание предсказуемое: checkout, установка PHP 8.2, `composer install`, `check.php`, `composer test`.

Заметьте, что CI не запускает ничего особенного — только те же команды, что вы вызываете локально. Как только в CI появляются уникальные шаги, воспроизвести падение на своей машине становится невозможно.

## Что автоматизировать, а что нет

Автоматизируйте то, что часто повторяется и имеет однозначный ответ «прошло/не прошло»: тесты, синтаксис, стиль, миграции, деплой. Не автоматизируйте то, что требует суждения: ревью, выбор архитектуры, приёмку фич. Инструмент экономит внимание для этих решений, а не заменяет их.

## Конец курса

Вы прошли путь от одного класса до дерева объектов с паттернами, тестами и автоматикой. Дальше полезно сделать три вещи: взять свой маленький проект и переписать его на разобранных принципах; прочитать исходники одного популярного пакета (там все паттерны из глав 8–12 в естественной среде); подключить `phpstan` на максимальном уровне к своему коду и починить то, что он найдёт.

Главная мысль курса, если оставить одну: зависимости — снаружи, поведение — рядом с данными, ветвление — там, где выбирают, а не там, где работают.

## Упражнение

1. Добавьте в `check.php` проверку: у каждого каталога `ChNN` есть либо `run.php`, либо тесты. Убедитесь, что скрипт по-прежнему возвращает `0`.
2. Добавьте в `composer.json` скрипт `"check": ["@lint", "@test"]` и запустите `composer -d course/code check`.
3. Установите хук `pre-commit`, сломайте любой файл (уберите `declare`) и попробуйте закоммитить. Затем почините и закоммитьте по-настоящему.
4. Возьмите свой проект и заведите в нём три скрипта Composer: `test`, `lint`, `check`. Дальше добавляйте в `check` всё, что сейчас делаете руками.
