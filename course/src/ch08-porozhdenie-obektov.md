# 8. Порождение объектов

Порождающие паттерны отвечают на один вопрос: кто и когда решает, объект какого класса создать. Вынесите это решение из бизнес-логики — и логика перестанет зависеть от конкретных классов.

Код главы: `course/code/Ch08/`.

```bash
php course/code/Ch08/run.php
```

## Factory Method: алгоритм здесь, выбор — в наследнике

```php
abstract class Importer
{
    abstract protected function createParser(): Parser;

    final public function import(string $raw): array
    {
        $tracks = $this->createParser()->parse($raw);
        usort($tracks, static fn (Track $a, Track $b): int => $a->title <=> $b->title);

        return $tracks;
    }
}
```

Базовый класс описывает, что делает импорт: разобрать и отсортировать. Чем именно разбирать, он не знает — за это отвечает `createParser()`, реализованный в `CsvImporter` и `M3uImporter`. Добавление формата не трогает `import()`, а `final` у `import()` гарантирует, что наследник подменит только точку расширения.

Когда это уместно: у вас есть устойчивый алгоритм и одна изменчивая деталь внутри него. Когда нет: если варьируется всё — вы городите иерархию там, где хватило бы обычного внедрения `Parser` в конструктор (глава 7). Между «фабричным методом» и «просто передать зависимость» чаще выигрывает второе; фабричный метод ценен, когда объект создаётся не один раз, а на каждый вызов и с учётом состояния.

## Abstract Factory: семейство, которое нельзя перепутать

```php
interface FormatKit
{
    public function parser(): Parser;
    public function writer(): Writer;
    public function name(): string;
}
```

`CsvKit` отдаёт `CsvParser` и `CsvWriter`, `M3uKit` — пару для M3U. Ошибка «прочитали CSV, записали M3U» становится невозможной по построению: вы выбираете семейство один раз, а дальше получаете согласованные части.

Само семейство ищется по имени формата среди зарегистрированных. В PHP 8.4 для этого есть готовая функция вместо цикла с `break`:

```php
$kit = array_find($kits, static fn (FormatKit $kit): bool => $kit->name() === $format)
    ?? throw new RuntimeException("Нет семейства для формата {$format}");
```

`array_find()` возвращает первый подошедший элемент или `null`. Рядом живут `array_find_key()`, `array_any()` и `array_all()` — предикат тот же, отличается только ответ. Все четыре принимают callback вида `fn($value, $key)`, так что искать можно и по ключу.

Это и есть смысл абстрактной фабрики — не «много фабричных методов», а гарантия совместимости продуктов между собой. Появится третий формат — добавите `JsonKit`, и ни один потребитель `FormatKit` не изменится.

Цена: каждый новый вид продукта в семействе (скажем, `validator()`) заставляет править интерфейс и все фабрики. Поэтому семейство должно быть стабильным по составу и изменчивым по реализациям.

## Prototype: клонировать дешевле, чем собирать

Когда заготовка собирается долго (загружена из базы, сконфигурирована десятком вызовов), новый объект проще склонировать:

```php
$evening = clone $template;
$evening->title = 'Вечер';
$evening->add(new Track('Drift', 270));
```

Главная ловушка — `clone` в PHP поверхностный: свойства-объекты остаются общими. Без этого метода добавление трека в копию меняло бы и оригинал:

```php
public function __clone(): void
{
    $this->tracks = clone $this->tracks;
}
```

В выводе примера `Утро: 1 трек(ов); Вечер: 2 трек(ов)` — доказательство, что копия отвязалась. Обратите внимание, что у `PlaylistTemplate` свойства изменяемые: прототип по природе мутабелен, иначе клонировать незачем. Неизменяемые объекты клонируют иначе — методами `withXxx()` из главы 5.

## Singleton: как устроен и почему обычно не нужен

```php
final class LibraryConfig
{
    private static ?self $instance = null;

    private function __construct(public readonly string $defaultFormat) {}

    public static function instance(): self
    {
        return self::$instance ??= new self('m3u');
    }
}
```

Механика: приватный конструктор закрывает `new`, статическое свойство хранит единственный экземпляр, `??=` создаёт его при первом обращении. `LibraryConfig::instance() === LibraryConfig::instance()` — `true`.

Теперь честная цена. Singleton — это глобальная переменная с приличным лицом. Класс, который внутри дёргает `LibraryConfig::instance()`, скрывает зависимость: по сигнатуре её не видно, в тесте не подменить (состояние живёт между тестами и течёт из одного в другой), а при появлении второй конфигурации придётся переписывать всех потребителей.

Что делать вместо: создайте объект один раз в точке сборки приложения и передайте его в конструкторы тем, кому он нужен. «Ровно один экземпляр» — это факт о вашей сборке, а не свойство класса. Если нужен централизованный доступ к сервисам, посмотрите главу 11 (Registry) и DI-контейнеры — они решают ту же задачу, не запирая объект внутри класса.

Singleton всё же встречается в жизни: обёртки над по-настоящему глобальным ресурсом (пул соединений) в маленьких скриптах. Знать его надо, тянуться к нему первым — нет.

## Упражнение

1. Добавьте `JsonKit` (`JsonParser` + `JsonWriter`) и прогоните через `$roundTrip` — код `$roundTrip` менять нельзя.
2. Сделайте `JsonImporter extends Importer`. Сколько строк понадобилось? Сравните с тем, что было бы при `match` по формату внутри `import()`.
3. Уберите `__clone()` из `PlaylistTemplate`, запустите пример и объясните полученные числа.
4. Перепишите `LibraryConfig` без синглтона: обычный класс с конструктором, экземпляр создаётся в `run.php` и передаётся туда, где нужен. Заведите в `run.php` вторую конфигурацию с форматом `csv` и убедитесь, что обе спокойно живут рядом.
