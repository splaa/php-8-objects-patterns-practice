# 4. Интерфейсы, абстрактные классы, трейты

Три инструмента, которые часто путают. Разделить их легко по вопросу «что именно они дают наследнику».

| Инструмент | Даёт тип | Даёт реализацию | Сколько штук на класс |
|---|---|---|---|
| Интерфейс | да | нет (только сигнатуры) | сколько угодно |
| Абстрактный класс | да | да, вместе с состоянием | один |
| Трейт | нет | да | сколько угодно |

Код главы: `course/code/Ch04/`.

```bash
php course/code/Ch04/run.php
```

## Интерфейс — договор без реализации

```php
interface Playable
{
    public int $seconds { get; }
    public string $duration { get; }
    public function label(): string;
}
```

С PHP 8.4 интерфейс требует не только методы, но и свойства — с указанием, какие операции над ними разрешены. Запись `{ get; }` означает «читать обязано быть можно»; есть и `{ get; set; }`, если контракту нужна запись. Это избавляет от целого слоя геттеров: раньше пришлось бы объявлять `seconds(): int` и `duration(): string` только ради того, чтобы интерфейс мог о них говорить.

Реализовать требование можно как угодно: обычным полем, `readonly`-полем или хуком. `MediaItem` отдаёт `public readonly int $seconds` из конструктора, `Jingle` — виртуальное свойство `public int $seconds { get => 5; }`. Контракт один, механика разная.

Интерфейс отвечает на вопрос «что я умею», ничего не говоря о том, «кто я». В примере `Player` принимает `list<Playable>` и работает и с музыкальным треком, и с пятисекундным джинглом рекламодателя, хотя общего предка у них нет:

```php
foreach ($this->queue as $item) {
    $total += $item->seconds;
    $lines[] = sprintf('%s (%s)', $item->label(), $item->duration);
}
```

Это и есть подстановка из главы 1, доведённая до практики. Классу-потребителю не нужно знать конкретные классы — ему нужен набор методов. Когда через полгода появится `Podcast`, `Player` менять не придётся.

Правило именования: интерфейс описывает способность (`Playable`, `Countable`, `Comparable`), а не сущность. И держите его узким: интерфейс из десяти методов реализовать никто не захочет.

## Абстрактный класс — частичная реализация плюс тип

```php
abstract class MediaItem implements Playable
{
    use FormatsDuration;

    public function __construct(
        protected readonly string $title,
        public readonly int $seconds,
    ) {}

    abstract public function label(): string;
}
```

`MediaItem` нельзя создать через `new` — это заготовка. Он приносит с собой состояние (`$title`, `$seconds`) и обязательство: каждый наследник обязан реализовать `label()`, иначе код не запустится.

Ключевая разница с интерфейсом — наследовать можно только один класс. Поэтому абстрактный класс выбирают, когда у потомков реально есть общие данные и общий код, а не просто общий набор имён методов.

Требование интерфейса `public int $seconds { get; }` здесь закрыто обычным `readonly`-свойством: наследник не сможет ни переопределить его поведение, ни записать в него после конструктора.

## Трейт — реализация без типа

```php
trait FormatsDuration
{
    public string $duration {
        get => match (true) {
            $this->seconds >= 3600 => sprintf('%d:%02d:%02d', ...),
            default => sprintf('%d:%02d', ...),
        };
    }
}
```

Трейт — это копипаста, которую делает компилятор: его содержимое вкладывается прямо в класс, и с 8.4 это касается не только методов, но и свойств с хуками. Типом трейт не является, поэтому `$item instanceof FormatsDuration` всегда возвращает `false` — молча, без единого предупреждения, — и подсунуть «любой объект с трейтом» в тайп-хинт нельзя.

Отсюда рабочая связка: **интерфейс объявляет, трейт реализует**. `Playable` требует свойство `duration`, `FormatsDuration` даёт готовый хук, `Jingle` берёт трейт и мгновенно становится полноценным `Playable`, не наследуя `MediaItem`. Обратное требование трейт выражает через обращение к `$this->seconds`: класс, взявший трейт, обязан дать источник данных — и компилятор это проверит, потому что `$seconds` требует сам интерфейс.

Обратите внимание на вывод примера: и `Track`, и `Jingle` — `Playable`, но `MediaItem` только `Track`. Плееру это безразлично, и это признак того, что типы расставлены правильно.

Если два трейта приносят метод с одним именем, PHP падает с фатальной ошибкой — конфликт разрешают через `insteadof` и `as`. Если вы дошли до этой конструкции, скорее всего, поведение просится в отдельный объект-помощник (композиция из главы 3).

## Как выбирать

Спросите: нужен ли мне *тип* для тайп-хинтов? Нужно ли *разделить состояние*? Ответы дают выбор. Только тип — интерфейс (и требуйте в нём свойства, а не геттеры, если речь о данных). Тип плюс общее состояние — абстрактный класс. Только повторяющийся код без родства — трейт, и то после того, как вы отвергли композицию.

По умолчанию: тайп-хинты — на интерфейсы, реализация — в классах, трейты — редко и тонким слоем.

## Упражнение

1. Добавьте `final class Podcast implements Playable` (шоу, номер, длительность) без наследования `MediaItem`, с трейтом `FormatsDuration`. Добавьте его в очередь плеера — код `Player` трогать нельзя.
2. Введите интерфейс `Skippable` с методом `canSkip(): bool`. Реализуйте его только в `Jingle` (`false`) и `Podcast` (`true`).
3. В `Player::run()` добавьте пометку `[пропуск запрещён]` для элементов, у которых `canSkip()` вернул `false`. Проверяйте способность через `instanceof Skippable` — это законный случай проверки типа: вы спрашиваете не «кто ты», а «умеешь ли».
4. Выведите `var_dump($jingle instanceof FormatsDuration)` и убедитесь своими глазами: `false`, хотя трейт в классе есть.
