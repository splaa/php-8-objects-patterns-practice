# 10. Поведение: Strategy, Observer, Command, Visitor

Поведенческие паттерны про то, как объекты распределяют между собой работу. Берём четыре, которые встречаются в реальном коде чаще всего, и только их рабочее ядро.

Код главы: `course/code/Ch10/`.

```bash
php course/code/Ch10/run.php
```

## Strategy: алгоритм как объект

В главе 7 мы уже пришли к нему, убирая сцепление. Формально: интерфейс объявляет операцию, реализации дают взаимозаменяемые алгоритмы, клиент получает нужный извне.

```php
interface Ordering
{
    /** @param list<Track> $tracks @return list<Track> */
    public function apply(array $tracks): array;
    public function name(): string;
}
```

`Player` принимает `Ordering` в конструктор и никогда не спрашивает, какой именно. `ByTitle` и `LongestFirst` — независимые классы, каждый тестируется отдельно.

Признак, что нужна стратегия: в методе завёлся `match` по типу поведения, и каждая ветка растёт. Признак, что не нужна: вариант ровно один и второй не предвидится.

Для совсем простых случаев в PHP роль стратегии играет замыкание (`callable`), и это нормально. Интерфейс выигрывает, когда у алгоритма есть имя, настройки или несколько методов.

## Observer: событие и подписчики

Плеер должен уведомлять статистику, историю и UI, но не должен о них знать.

```php
public function subscribe(PlayerListener $listener): void
{
    $this->listeners[] = $listener;
}
```

Издатель хранит список слушателей общего интерфейса и в нужный момент проходит по нему. В примере подписаны два наблюдателя: анонимный класс, печатающий строку, и `ScrobbleCounter`, считающий прослушивания. Добавить третий — не трогая `Player`.

Практические детали, которые важнее самой схемы:

- **исключение в одном наблюдателе роняет остальных**. Если подписчики независимы, оборачивайте вызов в `try/catch` и логируйте;
- **порядок вызова наблюдателей — не гарантия, а случайность**. Логика, зависящая от порядка, — ошибка проектирования;
- **отписка**. Долгоживущему процессу нужен `unsubscribe()`, иначе объекты не освободятся.

В PHP есть `SplSubject` и `SplObserver`, но свой интерфейс с осмысленным именем метода (`trackStarted()`, а не `update()`) читается лучше. В больших приложениях ту же идею реализуют шиной событий: те же наблюдатели, только регистрация централизована (PSR-14).

## Command: действие как объект

Команда упаковывает вызов вместе с аргументами. Как только действие стало объектом, его можно положить в очередь, залогировать, повторить и отменить:

```php
interface Command
{
    public function execute(): string;
    public function undo(): string;
}
```

`History::run()` выполняет команду и кладёт её в стек, `undoLast()` снимает верхнюю и зовёт `undo()`. В примере после отмены переименования плейлист снова «Утро», а добавленный трек остался — отменился ровно последний шаг.

Ключ к отмене — состояние, нужное для отката, команда хранит внутри себя (`RenamePlaylist::$previous`). Не все действия обратимы: отправленное письмо не вернуть. Для таких пишут компенсацию, а не отмену.

Команда также разделяет «кто просит» и «кто умеет»: кнопка интерфейса, консольная задача и обработчик очереди создают один и тот же объект команды.

## Visitor: новая операция без правки классов

Composite из главы 9 хорош, пока операций мало. Когда к дереву нужно добавлять отчёты, экспорт, валидацию — и всё это в классы дерева, — классы начинают знать про всё на свете.

Visitor выворачивает зависимость: дерево умеет только принимать гостя.

```php
public function accept(NodeVisitor $visitor): void
{
    $visitor->visitPlaylist($this);

    foreach ($this->children as $child) {
        $child->accept($visitor);
    }
}
```

`StatsVisitor` собирает статистику: сколько плейлистов, треков, секунд, какой трек самый длинный. Чтобы добавить экспорт в JSON, нужен новый визитёр — дерево не меняется.

Обход в примере пишет сам композит (`Playlist::accept()` рекурсивно зовёт детей). Альтернатива — обход внутри визитёра; тогда визитёр становится сложнее, зато можно менять порядок обхода.

Цена честная и известная: добавить новый **тип узла** дорого — придётся править интерфейс `NodeVisitor` и все его реализации. Visitor выгоден, когда типов узлов мало и они стабильны, а операций много и они прибывают. Если наоборот — не берите его.

## Как выбирать между ними

Спросите, что именно вы хотите сделать подменяемым. Алгоритм внутри одной операции — Strategy. Реакции на факт — Observer. Сам вызов, чтобы его хранить и откатывать, — Command. Набор операций над готовой структурой — Visitor.

## Упражнение

1. Добавьте стратегию `Shuffled` (используйте `shuffle()`), передайте её плееру. Ни `Player`, ни наблюдатели меняться не должны.
2. Научите `Player` переживать сбойного наблюдателя: добавьте слушателя, который бросает исключение, и сделайте так, чтобы остальные всё равно получили событие.
3. Добавьте `History::redo()`: отменённые команды складываются во второй стек и возвращаются обратно. Проверьте последовательность «выполнить, отменить, повторить».
4. Напишите `M3uExportVisitor`, который собирает строки `#EXTINF:` и в конце отдаёт готовый текст плейлиста. Классы `Track` и `Playlist` трогать нельзя — это и есть проверка того, что Visitor работает.
