# 6. Ошибки и исключения

Исключение — это способ вернуть из метода то, что не помещается в тип возврата: «я не смог». Возвращать `false` или `null` в таких случаях плохо тем, что вызывающий может молча не заметить провал.

Код главы: `course/code/Ch06/`.

```bash
php course/code/Ch06/run.php
```

## Иерархия: `Throwable`, `Error`, `Exception`

На вершине — интерфейс `Throwable`. Под ним две ветки:

- `Error` и потомки (`TypeError`, `ValueError`, `DivisionByZeroError`, `ArgumentCountError`) — ошибки самого кода. Обычно их не ловят: правят программу.
- `Exception` и потомки (`RuntimeException`, `LogicException`, `InvalidArgumentException`, `JsonException`) — ситуации, которые код предвидит.

`catch (Exception $e)` **не поймает** `TypeError`. Если вам действительно нужно поймать всё (например, в верхнем обработчике приложения), пишите `catch (Throwable $e)`.

Между `LogicException` и `RuntimeException` граница простая: логическая ошибка — та, которую можно было предотвратить кодом (неправильный аргумент, нарушенный порядок вызовов); рантайм-ошибка приходит извне (сеть, файл, данные пользователя).

## Свои классы исключений

```php
final class TrackNotFound extends RuntimeException implements LibraryError
{
    public static function withId(int|string $id): self
    {
        return new self("Трек {$id} не найден");
    }
}
```

Два приёма в четырёх строках.

**Именованный конструктор** собирает сообщение внутри класса: не нужно по всему проекту склеивать одинаковые строки, а сигнатура `withId()` подсказывает, что для этой ошибки важен идентификатор. Туда же удобно класть дополнительные поля (`public readonly int|string $id`), чтобы обработчик не парсил текст.

**Маркерный интерфейс** `LibraryError extends Throwable` ничего не требует, но позволяет написать `catch (LibraryError $e)` и поймать все ошибки нашей библиотеки, не перечисляя классы и не хватая заодно чужие. Это дешёвая и очень удобная штука: интерфейс объединяет исключения, которые наследуют разные базовые классы.

## Заворачивание причины

Низкоуровневые ошибки не должны вытекать наружу как есть: вызывающий не хочет знать, что внутри был `explode`. Но и терять их нельзя.

```php
} catch (Throwable $cause) {
    throw ImportFailed::atLine($number, $cause);
}
```

Третий аргумент конструктора исключения — `$previous`. Получается цепочка: наверху доменное «Импорт оборвался на строке 2», внутри техническое «Секунды не число». В выводе примера видно оба уровня: `$e->getPrevious()?->getMessage()`.

Запомните правило: ловить широко (`Throwable`) можно только на границе слоя и только чтобы тут же перебросить что-то осмысленное. Пустой `catch` без переброса — самая дорогая строка в проекте.

## `finally`

```php
try {
    foreach ($lines as $number => $line) { /* ... */ }
} finally {
    $this->log[] = 'закрыл источник';
}
```

`finally` выполняется всегда: и при нормальном выходе, и при исключении, и при `return` внутри `try`. Это место для освобождения ресурса — закрыть файл, откатить транзакцию, снять блокировку. В выводе примера строка «закрыл источник» есть и в успешном сценарии, и в упавшем.

Не делайте в `finally` `return`: он проглотит летящее исключение.

## Порядок `catch`

PHP берёт первый подходящий блок, поэтому частные типы идут раньше общих:

```php
} catch (TrackNotFound $e) {
} catch (LibraryError $e) {
}
```

Обратный порядок сделает первый блок мёртвым кодом. Несколько типов в одном блоке пишутся через `|`: `catch (TrackNotFound | ImportFailed $e)`. Переменную можно не объявлять вовсе: `catch (JsonException)`, если детали не нужны.

## Что ловить не надо

Не ловите исключение там, где не можете ничего с ним сделать. Если метод не умеет чинить проблему — пусть она летит выше, к тому, кто умеет: покажет пользователю сообщение, повторит запрос, запишет в лог. Промежуточные слои либо молчат, либо добавляют контекст через `$previous`.

Для целостной обработки на самом верху используйте `set_exception_handler()`: одно место, где приложение решает, что показать пользователю и что записать в лог.

## Упражнение

1. Добавьте в `TrackNotFound` публичное `readonly`-поле `$id` и заполняйте его в `withId()`. В обработчике выведите идентификатор, не разбирая текст сообщения.
2. Сделайте `Importer::import()` устойчивым: вместо остановки на первой битой строке собирайте ошибки и в конце, если они есть, бросайте `ImportFailed` с количеством проблем, а корректные треки возвращайте через поле исключения.
3. Добавьте `catch (TrackNotFound | ImportFailed $e)` и убедитесь, что оба типа попадают в один блок.
4. Зарегистрируйте `set_exception_handler()` и бросьте необработанное `TrackNotFound` — посмотрите, как выглядит единая точка обработки.
