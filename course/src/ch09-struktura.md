# 9. Структура: Composite, Decorator, Facade

Структурные паттерны отвечают за то, как объекты соединяются между собой. Три из них покрывают большую часть повседневных задач.

Код главы: `course/code/Ch09/`.

```bash
php course/code/Ch09/run.php
```

## Composite: дерево, с которым работают как с одним объектом

Плейлист может содержать треки и другие плейлисты. Наивное решение — везде проверять `if ($node instanceof Playlist)`. Composite убирает эти проверки: лист и ветка реализуют один интерфейс.

```php
interface PlaylistNode
{
    public string $title { get; }
    public int $seconds { get; }
    public function render(int $depth = 0): string;
}
```

У листа длительность — обычное `readonly`-свойство из конструктора. У ветки её нет физически, она считается по детям, и ровно для этого нужен хук из главы 4:

```php
public int $seconds {
    get => array_sum(array_map(static fn (PlaylistNode $n): int => $n->seconds, $this->children));
}
```

Снаружи разница незаметна: и `$track->seconds`, и `$playlist->seconds` — просто чтение свойства. Именно эта незаметность и есть цель композита.

Рекурсия получается бесплатно: вложенный плейлист — такой же `PlaylistNode`, и никто не спрашивает, кто он. В выводе примера «Дорога» содержит «Утро» и одиночный трек, а сумма 4695 секунд посчитана без единой проверки типа.

Цена паттерна — размывание интерфейса. Если у ветки есть `add()`, а у листа нет, вы либо объявляете `add()` в общем интерфейсе и заставляете лист бросать исключение, либо оставляете `add()` только в ветке и теряете единообразие. В примере выбран второй вариант: `add()` живёт в `Playlist`, и это честно — добавлять детей умеет только тот, у кого они бывают.

Composite подходит, когда структура действительно рекурсивна: меню, права доступа, отчёты, дерево комментариев. Для плоского списка он избыточен.

## Decorator: поведение наращивается снаружи

Задача: перед воспроизведением иногда нужно нормализовать громкость, иногда добавить нарастание, иногда и то и другое, в разном порядке. Наследованием это снова даёт комбинаторный взрыв.

Декоратор реализует тот же интерфейс, что и обёрнутый объект, и держит ссылку на него:

```php
abstract class PlaybackDecorator implements Playback
{
    public function __construct(protected readonly Playback $inner) {}
}

final class Normalized extends PlaybackDecorator
{
    public function play(): string
    {
        return $this->inner->play() . ' -> громкость -14 LUFS';
    }
}
```

Теперь цепочка собирается выражением: `new FadeIn(new Normalized(new RawPlayback($playlist)), 3)`. Порядок обёрток виден в выводе, и он важен: в `run.php` и в фасаде вложенность разная, поэтому строки отличаются. Для звука это буквально разный результат обработки.

Отличия от близких вещей: композиция из главы 3 делегирует работу **другому** типу, декоратор — **тому же** типу, поэтому обёртки можно складывать в любой глубине, а вызывающий код ничего не замечает. От наследования декоратор отличается временем: наследование фиксирует поведение при написании кода, декоратор — при сборке объекта, в рантайме.

Риск: длинная цепочка обёрток тяжело отлаживается — стек вызовов разрастается, и непонятно, кто добавил эффект. Два-три слоя читаются нормально, десять — нет.

## Facade: одна дверь вместо трёх

Фасад не добавляет логики. Он собирает несколько подсистем в одну понятную операцию:

```php
final class LibraryFacade
{
    public function eveningMix(array $spec): string
    {
        // собрать дерево Composite, обернуть декораторами, отрендерить
    }
}
```

Вызывающий пишет одну строку и не знает ни про `Playlist`, ни про `Normalized`. Это ценно на границах: контроллер, консольная команда, интеграция со сторонним кодом.

Два правила. Первое: фасад не должен содержать бизнес-правил — как только он начинает считать и решать, он превращается в тот самый `Manager` с низкой связностью. Второе: фасад не запрещает доступ к подсистемам напрямую. Кому нужен контроль — работает с `Playlist` и декораторами, кому нужна простота — берёт фасад.

## Как их различать в разговоре

Все три «оборачивают» объекты, но с разной целью. Composite делает много объектов похожими на один. Decorator делает один объект богаче, сохраняя его тип. Facade делает несколько объектов проще снаружи, вводя новый тип. Если вы назвали класс фасадом, а у него тот же интерфейс, что у обёрнутого объекта, — это декоратор.

## Упражнение

1. Добавьте в `PlaylistNode` требование `public int $count { get; }` (число треков). `Track` отдаст `1`, `Playlist` просуммирует детей хуком. Проверьте на дереве из примера: должно получиться 3.
2. Напишите декоратор `SkipSilence`, добавляющий к строке `-> пропуск тишины`, и соберите цепочку из трёх обёрток. Поменяйте их местами и объясните, чем отличается вывод.
3. Напишите декоратор `Logged`, который печатает `[лог] play()` перед делегированием. Он не меняет результат — это типичный «сквозной» декоратор.
4. Добавьте в `LibraryFacade` метод `quickPreview(string $albumTitle, array $tracks): string`, который собирает одноуровневый плейлист без декораторов. Убедитесь, что новый код в фасаде — только сборка, без вычислений.
