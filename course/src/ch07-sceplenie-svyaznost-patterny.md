# 7. Сцепление, связность, зачем паттерны

Две характеристики кода объясняют, почему один проект живёт пять лет, а другой переписывают через год.

Код главы: `course/code/Ch07/`.

```bash
php course/code/Ch07/run.php
```

## Связность: об одном ли этот класс

Связность (cohesion) высокая, когда все методы класса работают на одну задачу. Посмотрите на `TightExporter`:

```php
public function export(array $tracks, string $format): void
{
    $body = match ($format) {
        'm3u' => $this->toM3u($tracks),
        'json' => json_encode(...),
        default => throw new InvalidArgumentException("Формат {$format} не поддержан"),
    };

    echo '[жёсткий вариант] ', $body, PHP_EOL;
    file_put_contents('php://stdout', '[журнал] экспорт в ' . $format . PHP_EOL);
}
```

Он делает три разные вещи: выбирает формат, сериализует и выводит, да ещё пишет в журнал. У класса три причины измениться — новый формат, другой приёмник, другой журнал. Такой класс правят постоянно, и каждая правка рискует сломать соседнюю ответственность.

Признаки низкой связности видны без теории: в имени класса есть `Manager`, `Helper` или `Utils`; методы не используют общих свойств; описание класса требует союза «и».

## Сцепление: сколько я знаю о других

Сцепление (coupling) — это то, насколько класс завязан на конкретные другие классы. `TightExporter` жёстко сцеплен с `json_encode`, с `echo`, с форматом `m3u` и со списком допустимых форматов. Ни одну из этих деталей нельзя подменить снаружи, а значит, нельзя и протестировать отдельно.

Сцепление создаётся тремя способами: `new` конкретного класса внутри метода, обращение к статике и глобальным функциям с побочными эффектами, чтение конфигурации напрямую из окружения. Все три прячут зависимость: по сигнатуре метода не видно, что ему нужно.

Цель не «нулевое сцепление» — объекты обязаны разговаривать. Цель — сцепление с **абстракциями**, объявленными явно.

## Разворот: зависимости наружу

```php
final class Exporter
{
    public function __construct(
        private readonly Formatter $formatter,
        private readonly Output $output,
    ) {}

    public function export(array $tracks): void
    {
        $this->output->write($this->formatter->format($tracks));
    }
}
```

Класс сжался до одной строки логики и получил ровно одну ответственность: связать форматирование с выводом. Форматы стали отдельными классами (`M3uFormatter`, `JsonFormatter`), вывод — отдельным (`ConsoleOutput`). Зависимости видны в конструкторе — это **внедрение зависимостей**.

Что мы за это получили, видно в примере:

- новый формат добавляется снаружи. В `run.php` CSV-форматтер описан анонимным классом прямо на месте, и `Exporter` об этом не знает;
- появилась точка для теста: `MemoryOutput` собирает результат в массив, никакого экрана и файлов;
- исчез `match` по строке формата. Выбор реализации переехал туда, где собирают объекты.

Заметьте, мы не «применяли паттерн». Мы убрали жёсткое сцепление и получили Strategy — тот самый паттерн, который разберём в главе 10.

## Зачем нужны паттерны

Паттерн — это не библиотека и не обязательный элемент архитектуры. Это пара «типичная проблема — проверенное решение» плюс имя, на которое можно сослаться в обсуждении. Польза от паттернов трёх видов.

**Словарь.** «Давай вынесем это в декоратор» короче и точнее, чем три абзаца объяснений.

**Готовые компромиссы.** Каждый паттерн описан вместе с ценой: Singleton даёт единственный экземпляр, но вносит глобальное состояние; Observer развязывает отправителя и получателей, но усложняет отладку. Вы принимаете решение с открытыми глазами.

**Направление.** Почти все паттерны — вариации двух принципов: «программируйте на уровне интерфейса, а не реализации» и «предпочитайте композицию наследованию». Если вы поняли главу 3 и эту, половина каталога паттернов покажется вам очевидной.

И обратная сторона. Паттерн, применённый заранее, — это лишний слой, который нужно читать каждому новому человеку. Не начинайте с `AbstractFactoryBuilderInterface`. Начинайте с простого кода, а паттерн вводите в момент, когда конкретная боль стала повторяться.

## Упражнение

1. Добавьте `FileOutput`, пишущий в файл через `file_put_contents`. Проверьте, что `Exporter` править не пришлось.
2. Добавьте `LoggingOutput`, который в конструкторе принимает другой `Output`, печатает строку журнала и передаёт работу дальше. Соберите `new Exporter(new JsonFormatter(), new LoggingOutput(new ConsoleOutput()))` — вы только что написали декоратор из главы 9.
3. Перепишите `TightExporter` так, чтобы он стал тонкой обёрткой над новым `Exporter` (метод принимает строку формата и собирает нужные объекты). Это типичный приём, когда старый API надо сохранить, а внутренности заменить.
4. Напишите три предложения о том, какие причины изменения остались у `Exporter`. Если получилось больше одной — разбирайтесь, где ещё склеено.
