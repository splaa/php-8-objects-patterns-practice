# 14. Тесты PHPUnit на код предыдущих глав

Тесты — не про качество вообще, а про конкретную вещь: возможность менять код и за секунды узнавать, что вы сломали. Весь объектный дизайн предыдущих глав окупается именно здесь.

Код главы: `course/code/Ch14/` — тесты на классы из глав 5, 7, 10 и 12.

```bash
composer -d course/code install
composer -d course/code test
```

Вторая команда — тот самый скрипт из `composer.json`; напрямую это `./vendor/bin/phpunit`. Конфигурация лежит в `course/code/phpunit.xml.dist`: bootstrap на автозагрузку Composer и один набор тестов из каталога `Ch14`.

## Анатомия теста

```php
final class CatalogTest extends TestCase
{
    private Catalog $catalog;

    protected function setUp(): void
    {
        $this->catalog = new Catalog()
            ->add(new Track(1, 'Coastline', 215))
            ->add(new Track('drift-2024', 'Drift', 270));
    }

    public function testFindReturnsNullForUnknownId(): void
    {
        self::assertNull($this->catalog->find('нет такого'));
    }
}
```

Класс наследует `TestCase`, тестовые методы начинаются с `test` и ничего не возвращают. `setUp()` выполняется **перед каждым** тестом заново — состояние между тестами не протекает.

Имя метода — это утверждение на английском: `testGetThrowsForUnknownId` читается как предложение и сразу сообщает, что сломалось, когда упало. Внутри держитесь схемы «подготовили — выполнили — проверили»; одна проверяемая мысль на тест.

## Что утверждать

`assertSame()` сравнивает строго (`===`) — используйте его по умолчанию; `assertEquals()` допускает приведение типов и потому пропускает ошибки. Из остального в повседневной работе нужны `assertNull`, `assertCount`, `assertInstanceOf`, `assertTrue`/`assertFalse`, `assertNotSame`.

Проверка исключений — отдельный жанр:

```php
$this->expectException(RuntimeException::class);
$this->expectExceptionMessage('Трек 42 не найден');

$this->catalog->get(42);
```

Обратите внимание: ожидание объявляется **до** вызова. Всё, что написано после падающей строки, не выполнится.

## Параметризованные тесты

Когда логика одна, а данных много, не копируйте метод:

```php
#[DataProvider('lyricsCases')]
public function testLyricsPreview(?string $lyrics, string $expected): void { /* ... */ }

public static function lyricsCases(): iterable
{
    yield 'без текста' => [null, 'текста нет'];
    yield 'короткий текст' => ['We walked to the water at dawn', 'We walked to the wat...'];
}
```

Провайдер — статический метод, возвращающий наборы аргументов. Строковые ключи становятся именами случаев в отчёте, поэтому в выводе видно не `testLyricsPreview#1`, а «без текста».

## Дублёры: заглушка, мок, память

В `ExporterTest` три подхода к одной проблеме — не тащить в тест настоящую подсистему.

**Собственный дублёр.** `MemoryOutput` из главы 7 — обычный класс, который копит записи в массив. Самый скучный и самый надёжный вариант: без магии, зато можно проверить результат.

**Анонимный класс-заглушка.** Когда нужна фиксированная реакция на один вызов:

```php
$formatter = new class implements Formatter {
    public function format(array $tracks): string { return 'что угодно'; }
};
```

**Мок PHPUnit.** Когда проверять надо не результат, а сам факт взаимодействия:

```php
$formatter = $this->createMock(Formatter::class);
$formatter->expects(self::once())->method('format')->willReturn('тело');
```

Здесь нет ни одного `assert`, и тест всё равно может упасть: ожидание `once()` проверяется автоматически в конце. Пользуйтесь моками умеренно — тест, проверяющий вызовы, ломается при любом рефакторинге внутренностей, даже если поведение сохранилось.

И главное: все три дублёра возможны только потому, что зависимости внедряются через конструктор. Код с `new` внутри метода и синглтонами так протестировать нельзя — вот вам практическая цена решений из глав 7 и 8.

## Что тестировать в объектном коде

Тестируйте публичное поведение, а не приватные методы: они проверяются через публичные. Хорошие кандидаты видны прямо в примерах — граничные случаи (`find()` не нашёл), контракты (`get()` бросает исключение, а запись в `private(set)`-свойство даёт `Error`), неизменяемость (`withQuality()` не трогает оригинал), взаимодействие (`UnitOfWork` схлопнул два изменения в одну запись), инварианты (`IdentityMap` вернул тот же объект и не сходил в хранилище второй раз).

Отдельно стоит проверять то, что обещает не произойти. `testLazyAlbumHitsStorageOnlyOnFirstAccess` считает запросы к хранилищу: ноль после создания ленивого альбома, один после первого обращения и по-прежнему один после второго. Такой тест ловит потерю ленивости при рефакторинге — сама по себе она молча превращается в лишние запросы, а не в ошибку.

Начинайте тесты с той части кода, которую собираетесь менять или которая уже ломалась. Стопроцентное покрытие — плохая цель; быстрая обратная связь на важных местах — хорошая.

## Упражнение

1. Напишите `PlaylistTest` на композит из главы 9: длительность вложенного дерева и корректный отступ в `render()`.
2. Напишите `ImporterTest` на главу 6: проверьте, что битая строка даёт `ImportFailed`, а `getPrevious()` содержит `InvalidArgumentException`.

4. Сломайте `Catalog::get()` (пусть возвращает `null` вместо исключения), запустите тесты и посмотрите, какие именно упали. Верните как было — привыкайте доверять сигналу.
