# 12. Данные коротко: Mapper, Identity Map, Unit of Work, Lazy Load

Четыре идеи, которые лежат под любой ORM. Знать их полезно даже если вы никогда не напишете свой маппер: это словарь, которым описывают поведение Doctrine и её аналогов.

Код главы: `course/code/Ch12/`. Вместо базы — `Storage`: массив строк и журнал «запросов». Так видно, когда обращение к хранилищу происходит, а когда его удалось избежать.

```bash
php course/code/Ch12/run.php
```

## Data Mapper: сущность не знает про SQL

Разделение простое: `Track` хранит состояние и правила, `TrackMapper` умеет переносить его в хранилище и обратно.

```php
public function find(int $id): ?Track
{
    $known = $this->identityMap->get($id);

    if ($known !== null) {
        return $known;
    }

    $row = $this->storage->selectById($id);

    return $row === null ? null : $this->hydrate($row);
}
```

Превращение строки таблицы в объект называют гидрацией. Обратная сторона — `toRow()` в сущности либо извлечение полей в маппере.

Альтернативный подход — Active Record, когда у сущности есть собственные `save()` и `find()`. Он короче в мелких проектах и тяжелее в крупных: доменный объект оказывается связан с базой, а его нельзя создать в тесте без хранилища. Data Mapper дороже на старте, но домен остаётся чистым.

Практическое следствие: не давайте сущности знать про маппер. Как только `Track::save()` появился, разделение закончилось.

## Identity Map: один объект на одну строку

Что будет, если запросить трек `1` дважды? Без карты идентичности вы получите два разных объекта, и изменение одного не отразится в другом — классический источник «данные потерялись».

Карта — это просто индекс уже загруженных объектов по идентификатору:

```php
public function get(int $id): ?Track
{
    return $this->tracks[$id] ?? null;
}
```

В выводе примера `var_dump($first === $second)` даёт `true`, а в журнале один `SELECT ... WHERE id = 1`, хотя `find(1)` вызван дважды. Заодно карта работает как кеш на время запроса.

Границы применимости: карта живёт ровно один HTTP-запрос или одну консольную задачу. Долгоживущая карта — это утечка памяти и устаревшие данные. И она полезна лишь там, где объекты действительно запрашивают повторно.

## Unit of Work: одна запись вместо россыпи

Сохранять объект сразу после каждого изменения — значит гонять хранилище зря и терять целостность: половина изменений записалась, половина упала.

Unit of Work копит намерения и выполняет их вместе:

```php
$uow->registerDirty($first);
$uow->registerDirty($first);   // второй раз тот же объект
$uow->registerNew(new Track(null, 1, 'Hidden track', 92));

$uow->commit();                 // 2 записи, а не 3
```

Дубликат отсеялся, потому что изменённые объекты хранятся в массиве с ключом по идентификатору. В журнале видно один `INSERT` и один `UPDATE`.

В настоящем приложении `commit()` оборачивают в транзакцию: либо всё, либо ничего. Именно так работает `EntityManager::flush()` в Doctrine, а `persist()` — это `registerNew()`.

Открытый вопрос любой реализации — как узнать, что объект изменился. Мы регистрируем изменение руками; ORM делают это автоматически, сравнивая снимок состояния (dirty checking) или подставляя прокси-объекты.

## Lazy Load: не грузить то, что не спросили

Альбом почти всегда нужен, его треки — далеко не всегда. Раньше ленивость приходилось вписывать в сам класс: поле-заглушка, замыкание-загрузчик и `??=` в каждом методе. PHP 8.4 умеет это сам — **ленивые объекты**:

```php
public function lazy(int $id, string $title): Album
{
    return $this->reflector->newLazyGhost(function (Album $album) use ($id, $title): void {
        $album->__construct($id, $title, $this->tracks->findByAlbum($id));
    });
}
```

`ReflectionClass::newLazyGhost()` создаёт объект-призрак: экземпляр `Album` уже существует, у него правильный класс и тип, но свойства не инициализированы. Первое же обращение к состоянию запускает инициализатор, тот вызывает настоящий конструктор — и дальше объект ничем не отличается от обычного.

Ключевое здесь — в самом `Album` нет ни строчки про ленивость. Обычный класс с `readonly`-свойствами; всё знание о том, что загрузка отложена, лежит в мапперe. В выводе примера видно: `$album instanceof Album` — `true`, после создания запросов ноль, `SELECT ... WHERE album_id = 1` появляется при первом обращении, повторное обращение новых запросов не даёт.

Вторая стратегия — `newLazyProxy()`: инициализатор не заполняет объект на месте, а возвращает настоящий экземпляр, которому прокси потом переадресует обращения. Её берут, когда создание объекта вам не принадлежит (его делает чужая фабрика). Расплата — две разные идентичности: прокси и реальный объект не `===` друг другу, и это ломает Identity Map, если о нём забыть.

Что считается «обращением к состоянию», стоит помнить: чтение и запись свойства, `isset`, клонирование, сериализация, `foreach` по свойствам. Вызов метода, который до состояния не дотрагивается, инициализацию не запускает.

Обратная сторона известна как «проблема N+1»: цикл по ста альбомам с ленивыми треками даст сто один запрос. Лечится жадной загрузкой — одним запросом сразу за всеми нужными данными. Правило простое: лениво — для необязательных данных, жадно — когда вы уже знаете, что обойдёте всю коллекцию.

## Что уносить

Эти четыре идеи решают четыре разные проблемы: связь домена и хранилища, дубли объектов, россыпь записей, лишние запросы. В продакшене их реализует ORM. Ваша задача — узнавать симптомы: два объекта на одну строку, десять `UPDATE` подряд, сто запросов на страницу.

## Упражнение

1. Добавьте `TrackMapper::delete(Track $track): void` и `UnitOfWork::registerDeleted()`. Проверьте по журналу, что удаление тоже попадает в общий коммит.
2. Сделайте так, чтобы `find()` для несуществующего идентификатора не ходил в хранилище дважды (кеш промахов). Подумайте, чем это опасно.
3. Замерьте «проблему N+1»: создайте два ленивых альбома, обойдите их в цикле, посчитайте запросы. Затем добавьте метод, который грузит треки обоих альбомов одним вызовом, и сравните числа.
4. Добавьте в `UnitOfWork::commit()` имитацию сбоя на втором объекте и опишите в комментарии, что должно происходить с уже записанными изменениями и почему настоящая реализация требует транзакции.
5. Сделайте так, чтобы чтение `$album->id` не запускало загрузку: воспользуйтесь `ReflectionProperty::setRawValueWithoutLazyInitialization()` в `AlbumMapper` и проверьте по счётчику запросов, что ленивость сохранилась.
